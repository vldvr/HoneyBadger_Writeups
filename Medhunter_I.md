# МёдХантер I: ранний доступ

**CTF:** AvitoCTF · SPbCTF
**Категория:** Web / Cloud / Combo · **Сложность:** Easy

> МёдХантер - портал вакансий Медоедска: медоеды публикуют резюме и откликаются на вакансии, компании ищут когтистых сотрудников.
> Без PDF-версии резюме вас не рассмотрит ни одна солидная компания, а генерация PDF доступна только участникам закрытого тестирования. Нужно раздобыть **действующий код приглашения**.

**Флаг:** `avito{ExcLu51V3_pDF_4cc3Ss_3NAblEd}`

---

## TL;DR

В приложении есть серверный fetch по пользовательскому URL, который **рефлектит тело ответа** в ошибке парсинга. Это SSRF. Направляем его на метадату инстанса Yandex Cloud и читаем **cloud-init user-data** - там развёртывается `.env` с `PDF_BETA_INVITE_CODE`. Этот инвайт-код и есть флаг.

---

## 1. Разведка

Приложение - клон HeadHunter. Заполняешь резюме, откликаешься на вакансии, а генерация PDF залочена за "закрытым тестированием" и требует инвайт-код.

Что бросается в глаза:

- Генерация PDF - отдельный процесс (headless-рендер). Рассматривали инъекцию в поля резюме, попадающие в рендер, но рабочим оказался другой примитив - SSRF (ниже).
- Где-то в приложении бэкенд сам **ходит по переданному URL** и пытается разобрать ответ. При скармливании "неправильного" ответа возвращается говорящая ошибка:

  ```
  Exception: invalid character '#' looking for beginning of value
  ```

  Это ошибка Go-шного `encoding/json`: сервер сделал `json.Unmarshal` над телом ответа и подавился на первом символе `#`. Значит, во-первых, это **SSRF**, а во-вторых, тело ответа **рефлектится** обратно к нам. Идеально для чтения внутренних ресурсов.

---

## 2. SSRF → метаданные инстанса

Раз бэкенд крутится в Yandex Cloud, самая вкусная цель для SSRF - **сервис метаданных** на `169.254.169.254`. Через IMDSv1-мост он отдаёт `user-data` без спец-заголовков:

```
http://169.254.169.254/latest/user-data
```

(GCP-совместимый вариант - `http://169.254.169.254/computeMetadata/v1/instance/attributes/user-data` с заголовком `Metadata-Flavor: Google`.)

Подсовываем этот URL в уязвимый fetch. Сервер тянет `user-data`, пытается распарсить как JSON, спотыкается о `#cloud-config` - и **вываливает всё тело в ошибку**. Тот самый `#` из `invalid character '#'`.

> **[уточнить]** точный эндпоинт/поле, через которое проходит SSRF - вписать при перепрохождении.

---

## 3. Добыча: cloud-init user-data

В рефлектнутом ответе - полный cloud-config, который разворачивает приложение. Ключевое - запись `.env`:

```yaml
#cloud-config
write_files:
  - path: /opt/app/.env
    permissions: "0600"
    content: |
      POSTGRES_USER=hrportal
      POSTGRES_DB=hrportal
      EMPLOYER_REGISTRATION=
      PDF_BETA_INVITE_CODE=avito{ExcLu51V3_pDF_4cc3Ss_3NAblEd}
      ...
```

`PDF_BETA_INVITE_CODE` - это и есть искомый "код приглашения закрытого тестирования", он же флаг задачи.

> В том же `.env` лежат ключи Object Storage, `CALLBACK_SECRET` и прочие креды окружения, а `start.sh` показывает, как инстанс тянет IAM-токен из метадаты и логинится в `cr.yandex`. Это материал для следующих частей серии - в рамках Части I опускаю.

## 5. Выводы

- **SSRF, рефлектящий тело ответа** (тут - через ошибку JSON-парсинга), моментально превращается в чтение внутренних ресурсов. Сообщения об ошибках, отдающие сырой ответ наружу, - находка для атакующего.
- **Метадата облака - первая цель SSRF.** `169.254.169.254` через IMDSv1-мост отдаёт `user-data`, а туда часто кладут cloud-init с секретами прямо в открытом виде.
- **Секреты в user-data = секреты для всех, у кого есть SSRF.** Инвайт-код, ключи хранилища и токены не должны лежать в метадате в plaintext; их место - в защищённом хранилище секретов с доступом только у сервис-аккаунта.
