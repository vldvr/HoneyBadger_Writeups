# OnMute - writeup

**Категория:** Web · JavaScript
**Сложность:** Medium (447)

> OnMute - музыкальная площадка, где суровая мед-фанбаза следит за чистотой текстов. Любой намёк на слабость - страх, нежность, вежливость - мгновенно уходит под цензуру. В одном из треков автор припрятал отсылку для своих - её тоже вырезали. Нужно победить цензуру и достать полные тексты.

---

## TL;DR

Фильтр контента переиспользует **один и тот же объект `RegExp` с флагом `g`** на всю сессию, кэшируя его в in-process `Map`. Из-за stateful-семантики `lastIndex` у глобальных регэкспов один вызов `RegExp.prototype.test()` внутри команды `/censor` сдвигает внутренний указатель и **не сбрасывает его**. Следующая проверка того же regex стартует не с начала строки - и слово `original` в команде `/original <id>` проскакивает мимо блокировки. Команда доходит до обработчика и возвращает оригинальный текст.

Эксплойт в два запроса в одной сессии:

1. `/censor <start> <end>` - навести на забаненное слово в тексте трека (получить ответ «распознан как нарушающий правила»).
2. `/original <track_id>` - в той же сессии сразу следом.

## Разбор

### Точка входа

Роут `POST /:id/comment` сначала прогоняет весь текст через фильтр, и только потом парсит команды:

```js
const scan = checkContent(text, req.sessionId);

if (scan.blocked) {
  // ... блокируем, до parseCommand дело не доходит
  return res.json({ ok: false, reason: 'Заблокировано фильтром контента', ... });
}

const cmd = parseCommand(text);
if (cmd) {
  const result = await handleCommand(cmd, { trackId, req });
  // ...
}
```

Команда `/original` в `commands.js` своей собственной проверки на блок-лист **не имеет**:

```js
case 'original': {
  const original = await getOriginalText(cmd.trackId);
  if (!original) return { type: 'bot', message: `Трек #${cmd.trackId} не найден.` };
  return { type: 'bot', command: '/original', message: original };
}
```

Значит единственный барьер между атакующим и оригинальным текстом - это `checkContent`, срабатывающий на слово `original` из блок-листа (`blocklist.js`, первое слово в массиве). Всю задачу сводит к тому, чтобы `checkContent` **не** заблокировал строку `/original 5`.

### Уязвимость: общий stateful regex

Фильтр собирает регэксп один раз на сессию и кладёт в модульный `Map`:

```js
const policies = new Map();

function getPolicy(sessionId) {
  if (!policies.has(sessionId)) {
    policies.set(sessionId, {
      id: sessionId,
      re: new RegExp(
        `(?:${BLOCKED_WORDS.join('|')})(?=[\\s.,!?;:)}\\]"'»]|$)`,
        'gi',
      ),
    });
  }
  return policies.get(sessionId);
}
```

Флаг `g` делает объект **stateful**: и `exec()`, и `test()` при успешном совпадении продвигают `re.lastIndex` на позицию конца матча, и следующий вызов начинает поиск **оттуда**, а не с нуля. `lastIndex` сбрасывается в 0 только когда матча не найдено.

В модуле две функции используют этот общий regex по-разному:

```js
export function checkContent(text, sessionId) {
  const { re } = getPolicy(sessionId);
  const violations = [];
  let m;
  while ((m = re.exec(text)) !== null) {       // дренирует до null -> lastIndex сбрасывается сам
    violations.push({ match: m[0], index: m.index });
  }
  return { blocked: violations.length > 0, violations };
}

export function matchesPolicy(fragment, sessionId) {
  const { re } = getPolicy(sessionId);
  return re.test(fragment);                    // одиночный test(): при матче lastIndex НЕ сбрасывается
}
```

- `checkContent` сам по себе безопасен: цикл `while (exec !== null)` всегда доходит до `null`, что сбрасывает `lastIndex` в 0. Изолированно фильтр отрабатывает корректно.
- `matchesPolicy` - **единственный одиночный `test()`**. Если он находит совпадение, `lastIndex` остаётся сдвинутым, и это состояние переживает запрос, потому что regex-объект общий на всю сессию.

`matchesPolicy` вызывается ровно в одном месте - в обработчике `/censor`:

```js
const fragment = track.text.slice(cmd.start, cmd.end);
const flagged = matchesPolicy(fragment, req.sessionId);   // <-- порча lastIndex
```

### Как складывается эксплойт

1. **Запрос 1: `/censor <start> <end>` на забаненное слово.**
   Строка `/censor 12 18` не содержит банвордов, поэтому `checkContent` её пропускает. `parseCommand` распознаёт команду, `handleCommand` вырезает `fragment` из текста трека и вызывает `matchesPolicy(fragment, sessionId)`. Так как фрагмент - это забаненное слово (страх / нежность / отсылка автора и т.п.), `test()` возвращает `true`, а `re.lastIndex` встаёт на конец совпадения и **остаётся ненулевым**.

   Признак успеха - ответ бота: «Фрагмент «…» распознан как нарушающий правила и отправлен на приоритетную цензуру». Если пришло обычное «принят» - матча не было, `lastIndex` чист, и шаг не сработает.

2. **Запрос 2: `/original <track_id>` в той же сессии.**
   `checkContent` берёт **тот же самый** закэшированный regex с уже ненулевым `lastIndex`. Поиск по строке `/original 5` стартует не с индекса 0, а с унаследованной позиции, из-за чего слово `original` в начале строки проскакивает. Других банвордов в строке нет - `exec` немедленно возвращает `null`, `checkContent` отдаёт `blocked: false`, и `lastIndex` заодно сбрасывается.

   Строка беспрепятственно доходит до `parseCommand` (у него отдельный регэксп `^\/original\s+(\d+)\s*$` без флага `g`, никакого разделяемого состояния), команда выполняется, `handleCommand` возвращает полный оригинальный текст без цензуры.

### Почему сессия важна

`req.sessionId` берётся из персистентной куки `onmute_sid` (TTL сутки):

```js
let sid = req.cookies?.[COOKIE_NAME];
if (!sid) { sid = uuidv4(); res.cookie(COOKIE_NAME, sid, { httpOnly: true, ... }); }
req.sessionId = sid;
```

Оба запроса должны идти под одной кукой - иначе `getPolicy` создаст новый regex и порча `lastIndex` не перенесётся между запросами. Отправляя оба запроса подряд в одной сессии, мы гарантируем общий regex-объект.

## Эксплуатация (шаги)

1. Открыть трек, получить его текст и найти в нём слово из блок-листа (`blocklist.js`) длиной ≤ 10 символов - лимит `/censor` (`cmd.end - cmd.start > 10` режется). Короткие подходят: `блин`, `чёрт`, `ужас`, `фигня` и т.п.
2. Посчитать позиции символов `<start>`/`<end>` этого слова в тексте трека.
3. Отправить `/censor <start> <end>`. Убедиться, что бот ответил «распознан как нарушающий правила» (flagged).
4. Сразу следом в той же сессии отправить `/original <track_id>`.
5. Бот вернёт полный оригинальный текст трека - вместе со спрятанной автором отсылкой.

## Первопричина и фикс

Корень - **разделяемое мутабельное состояние глобального регэкспа**. Любой из вариантов чинит проблему:

- Не хранить общий `RegExp` с флагом `g`. Собирать regex локально на каждый вызов, либо хранить только строку паттерна и создавать объект внутри функции.
- Сбрасывать `re.lastIndex = 0` перед каждым использованием.
- Убрать флаг `g` там, где нужна только булева проверка (`matchesPolicy`). Без `g` `test()` не ведёт состояние.
- Использовать `String.prototype.match` / `matchAll` на свежих объектах вместо переиспользуемого `exec`/`test`.

Дополнительно стоит валидировать команды на блок-лист **внутри** обработчика (в частности `/original`), а не полагаться на единственную проверку всего текста на входе в роут.

## Заметки

- В сообщении об ошибке фильтра (`botText`) спрятан текст через Unicode Tag characters (U+E00xx) - невидимые символы после эмодзи ⛔. Декодирование ловит игроков, решающих с помощью ИИ агента - что было запрещено в этом CTF и к основному решению отношения не имеет.
